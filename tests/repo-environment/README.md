# Repo Environmentの検証

要求の参照元は[開発依頼書](../../PROJECT_BRIEF.md)。プラグイン単体の使い方は[配布README](../../plugins/repo-environment/README.md)を参照する。

## ローカルでの構造確認

開発用のPython 3.10以降で、リポジトリルートから実行する。外部ライブラリは不要で、製品の実行時依存ではない。

```sh
python3 tests/repo-environment/check_package.py
git diff --check
```

チェッカーは配布フォルダだけを一時ディレクトリの対象へコピーし、最低限のメタデータとskillの存在、Markdownのローカルリンクがパッケージ内で解決することを確認する。Codexの正式なschema検証、インストール、skillの判断品質は検証しない。

## デスクトップでの受け入れ確認

配布元とは別の検証用Gitリポジトリを用意し、試験ごとに初期状態と差分を保存する。実際に利用するCodexデスクトップアプリの版、OS、WSLの有無、pluginの版、対象コミットを記録する。ユーザー全体の設定変更が必要になったら、その適用範囲を確認するまで止める。

| シナリオ | 準備・依頼 | 確認する結果 | 対応する要求 |
| --- | --- | --- | --- |
| 対象限定の導入 | 配布READMEの手順で検証先へ導入。別の未導入リポジトリも開く | 対象で2つのskillを呼べる。別の対象へ意図せず有効化されない。全体設定とキャッシュの変化を区別する | AC-14、AC-15 |
| 相談メモと空リポジトリ | メモには目的と未採用の候補技術を記載。別の空リポジトリでもsetupを呼ぶ | 採用済みと候補を区別し、必要な判断だけ相談する | AC-01、AC-02、AC-05 |
| 既存構成と小規模な対象 | 既存の指示・文書・実行可能な検証コマンドを置く | 再利用し、不要な文書や構成を追加しない。実際に実行した検証を報告する | AC-03、AC-04、AC-06 |
| 再実行と手動編集 | 一度適用後、同じ依頼を再実行。さらに人が指示の一部を編集してmaintenanceを呼ぶ | 重複や不要な差分を作らず、手動変更との競合は無言で上書きしない | AC-07、AC-08 |
| 拡張の探索と採用 | 対象の不足を1つ指定し、候補の探索を依頼する。採用前と採用後を分けて観察する | 一次情報・適合理由・導入範囲を示し、合意した候補だけを導入。認証やツール不足は未完了として報告する | AC-05、AC-06、AC-10、AC-16 |
| 関連リポジトリ | ローカルに文書用リポジトリを作り、参照を登録する。入口を移動して再確認する | 共有情報とローカルパスを分け、相手へ書き込まない。移動・参照不能を未確認として扱う | AC-10、AC-14、AC-17 |
| 部分失敗 | 適用途中の書き込みを拒否するなど、制御できる失敗を起こす | 適用済み・未適用と復旧方法を示し、既存のユーザー差分を保護する | AC-11 |
| 更新・削除 | pluginを更新し、次に対象だけ無効化・削除する | 導入先の合意済み成果物が残り、共有設定や別の利用先を巻き込まない | AC-09、AC-12 |
| 検証後の変更 | レビュー・検証後に対象を変更する | 古い結果を現在の確認済み証拠にしない | AC-13 |

初期版を実用可能と判断する前に、上記を配布元以外で実施する。指示文に要件が書かれていることだけで合格にしない。構造確認と実動確認の結果は別々に記録する。
