# リポジトリの構成・運用方針

## 管理する範囲

AI開発ワークフロー向けの複数プラグインを、1つのリポジトリで管理します。最初の製品はセットアップ・メンテナンス拡張です。[開発依頼書](../PROJECT_BRIEF.md)はこの拡張の要求を扱います。

同じ場所で方針の変更や比較実験を扱いながら、利用者が必要なプラグインだけを選べる構成にします。公開範囲や保守担当を独立させる必要が生じたら、リポジトリの分割を検討します。

## 配置方針

現在の配置と、将来追加する配置を次に示します。新しいディレクトリは内容が必要になった段階で作成します。

```text
agent-env-kit/
├── README.md                  # 全体の案内・プラグイン一覧
├── AGENTS.md                  # このリポジトリでの作業指示
├── PROJECT_BRIEF.md            # 最初の拡張の要求
├── docs/
│   └── repository.md          # 構成・運用方針
├── plugins/
│   └── repo-environment/      # 最初のプラグインの配布対象
└── tests/
    └── repo-environment/      # 構造確認・受け入れ手順・検証記録

将来の配置:
plugins/<plugin-name>/         # 追加するプラグインの配布対象
tests/<plugin-name>/           # 追加するプラグインの検証手順・fixtures
docs/experiments/              # 比較実験の記録
```

各プラグインの内部構成は提供形式の確認後に決めます。最初の[Repo Environment](../plugins/repo-environment/README.md)はmanifest、2つのskills、共通の参考資料で構成します。利用者向けのREADMEには、用途、導入、利用、更新、無効化・削除、制約を実装に合わせて記載します。実行時に必要な手順や参考資料もプラグイン内に置き、親の開発資料への参照を実行の前提にしません。

配布元の開発資料、検証用ファイル、導入先に生成する成果物は、それぞれの役割を区別します。導入先へリポジトリ全体をコピーせず、採用した配布方式で必要な対象だけを提供します。

## プラグインと比較実験の単位

- 独立して選択・利用する意味がある機能を、別プラグインとして分けます。確認項目ごとに細分化する必要はありません。
- 同じ目的の別案を継続的に切り替えて試す場合は、別のプラグインディレクトリで管理します。一時的な変更案はブランチで扱います。
- 各プラグインの状態は[ルートREADMEの一覧](../README.md)に記録します。実験中・利用可能・廃止などの状態変更だけを理由に、ディレクトリを移動する運用にはしません。
- 共通ライブラリ、共通ビルド基盤、全エージェント対応の抽象化は、実際の重複や要件を確認してから検討します。

これにより、機能の組み合わせと別案の比較を同じ場所で扱い、初期段階の構成変更や共通化の負担を抑えます。

## 文書の正本

| 文書 | 管理する内容 |
| --- | --- |
| [ルートREADME](../README.md) | 全体の目的、プラグイン一覧と状態、文書の入口 |
| [AGENTS.md](../AGENTS.md) | このリポジトリで作業する際の短い指示と検証の入口 |
| この文書 | 配置、開発・文書管理の方針、リポジトリ全体の重要な判断と理由 |
| [PROJECT_BRIEF.md](../PROJECT_BRIEF.md) | セットアップ・メンテナンス拡張の要求、提案、未決定事項、受け入れ条件 |
| 各プラグインのREADME・仕様 | そのプラグインの利用方法と具体化した振る舞い |
| 実験記録 | 比較の仮説、条件、結果、採否と理由 |

文書は日本語を基本とし、説明的な見出し、リポジトリ相対リンク、必要なコマンド例を使います。同じ決定を複数箇所で手動管理せず、正本へのリンクで案内します。常設の指示は短く保ち、詳細を必要時に参照できるようにします。

要求・提案・未決定を区別し、候補を採用済みとして記載しません。依頼書の内容を詳細仕様へ移した場合は、元の文書に移転先と現在の正本を明示します。原資料の削除は別途判断します。

重要な判断は当面この文書に理由とともに記録します。ADR、ロードマップ、進捗管理文書は、独立した管理が必要になった時点で追加します。

## 実験と検証

実験記録には、仮説、比較対象のバージョンまたはコミット、エージェントと実行環境、対象リポジトリの条件、実施手順、結果、採否と理由を簡潔に残します。秘密情報の値は記録しません。実行条件や対象が変わった場合、過去の結果をそのまま新しい対象の検証済み証拠として扱いません。

検証手順とfixturesは `tests/<plugin-name>/` に置きます。導入・メンテナンスの実動検証は、配布元とは別の検証用リポジトリで行います。再現用の入力例と、実際に変更を適用する作業先を区別してください。

受け入れ条件は対象プラグインの要求から選びます。セットアップ・メンテナンス拡張では、依頼書のAC-01〜17を用いて、新規・既存構成、再実行、手動変更、部分失敗、拡張の選定、関連リポジトリ参照などを検証します。他の拡張には、その振る舞いに合った条件を定めます。

文書変更ではリンク、コマンドの正確さ、正本との整合性を確認します。実装を導入したら実際のbuild・テスト・実行コマンドを文書化し、必要な検証を追加します。現在はPython標準ライブラリのみの[パッケージ構造確認](../tests/repo-environment/README.md)と、開発用のRuffによる整形・lintがあります。buildシステム、外部テストフレームワークは導入していません。

検証結果は成功・失敗・未実行・対象外を区別し、未確認事項と次に必要な確認を示します。

### Pythonの整形・lint

Ruffはこのリポジトリの開発用ツールです。バージョンは[requirements-dev.txt](../requirements-dev.txt)、設定は[ruff.toml](../ruff.toml)で管理します。Python 3.10を対象に、基本的なエラー検出とimport順序のルールを適用し、formatは既定値を使います。

初回はリポジトリルートで仮想環境を用意します。

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
```

Pythonファイルの追加・編集後は、変更したファイルだけを指定して実行します。以下のパスは対象のファイルへ置き換えてください。

```sh
.venv/bin/ruff check --fix path/to/script.py
.venv/bin/ruff format path/to/script.py
.venv/bin/ruff check path/to/script.py
.venv/bin/ruff format --check path/to/script.py
```

自動修正後も残るlintエラーはコードを修正し、最後の2つの確認が成功するまで繰り返します。`--unsafe-fixes` は使いません。Windowsでは `.venv/bin/` を `.venv/Scripts/` に読み替えます。

全Pythonファイルを変更せず確認する場合は、次を実行します。

```sh
.venv/bin/ruff check .
.venv/bin/ruff format --check .
```

この手順は[AGENTS.md](../AGENTS.md)から常設指示として適用します。skillの選択やhooksの実行を前提にせず、エージェントが編集後にコマンドを実行する運用です。Ruffと仮想環境はプラグインの配布・実行時依存に含めません。

## 未決定事項

提供形式や対応環境はプラグインごとに決めます。Repo Environmentの確定要求と未決定事項は[開発依頼書](../PROJECT_BRIEF.md)、現在の配布手順は[配布README](../plugins/repo-environment/README.md)を正本とします。初期のデスクトップ実動検証、OS・WSL・バージョン範囲の確認が残っています。
