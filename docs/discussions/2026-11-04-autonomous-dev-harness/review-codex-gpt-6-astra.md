## 全体評価

プロジェクトごとに必要な仕組みを選び、人間が重要な判断に集中するという目的は妥当である。

実現に向けて最も詰めたいのは、AIがどこまで自律的に進めてよいか、その判断を何で裏づけ、失敗したらどう戻すかである。skillsやレビュー役を増やすだけでは、この部分は安定しない。

[開発依頼書](../../../PROJECT_BRIEF.md)と[開発フロー支援の要件・課題](../../plugins/repo-environment/development-workflow.md)には、承認範囲の引き継ぎ、確認結果の陳腐化、レビュー対象の識別などがすでに含まれている。以下では、既存の観点は具体化が必要な点として扱う。

## 1. 「設定を促す」と「設定を適用する」の境界

「プラグイン自体は開発環境を直接設定するものではない」は、二通りに読める。

- 調査・提案までを担当し、設定作業は別の手段に委ねる。
- 固定の設定を自動配布せず、導入先を調査して合意後に設定する。

既存の開発依頼書は後者である。目的からも、調査、提案、必要な合意、適用、検証、見直しまで支援する方が自然と考える。提案だけで終えると、人間が設定作業を取り次ぐ負担が残る。

環境を整備する機能と、日々の開発・レビューを進める機能は、責務として区別すると整理しやすい。別プラグインにするかは、独立して利用する需要を確認してから決めればよい。

## 2. 操作ごとの委任範囲

「重要なところは人間が確認する」だけでは、確認過多にも確認漏れにもなる。導入先ごとに、例えば次のような方針を合意すると具体化できる。

| 操作 | 委任方針の例 |
| --- | --- |
| 合意済み設計の実装、関連テスト、通常の修正 | 自律実行 |
| 調査や比較用の試作 | 隔離した範囲で自律実行 |
| 新規依存、公開API変更、データ保存方式の変更 | 判断材料をまとめて相談 |
| push、merge、公開、配備 | それぞれ別に実行条件を決める |
| 検証ルールの弱体化、権限拡大 | 通常の修正権限に含めない |

これは全プロジェクト共通の固定ルールではなく、何を委任するかを決めるための枠組みである。

実装の承認をmergeや本番配備の承認として扱わないこと、合意済み範囲は何度も確認しないことが重要である。既存文書にある承認範囲の考え方を、実際の操作へ対応づけたい。

## 3. skills・hooks・CI・権限設定の役割

skillsは手順や判断観点を共有する手段として適している。ただし、descriptionによる選択を、必須チェックが必ず実行される保証にはできない。公式説明でも、descriptionはモデルがskillを選択するための情報という位置づけである。[OpenAI Skills](https://developers.openai.com/plugins/concepts/skills)

hooksには、結果をエージェントが解釈する機能に加え、ホストが結果を読んで操作を拒否する機能もある。ただしイベントによって異なり、例えばClaude Codeの実行後hookは、すでに行われた操作を阻止できない。[Claude Code Hooks](https://code.claude.com/docs/en/hooks)

| 仕組み | 主な役割 |
| --- | --- |
| 常設指示・skills | 作業の進め方、判断、文脈の参照 |
| 独立した検証コマンド | 再現可能なチェックの実体 |
| エージェントhooks・Git hooks | 適切なタイミングで検証を呼ぶ |
| CI・統合条件 | 共有する変更の検証と統合可否 |
| 権限・sandbox | 実行できる操作の制限 |

未実行、タイムアウト、検証基盤の故障を合格と区別する必要がある。AIがチェックを通すためにテストやルールを弱めた場合、その変更自体をレビュー対象にする。

## 4. エージェント間での共通化と互換性

skillsの本文やレビュー観点は共有しやすい。一方、呼び出し方、利用可能なツール、サブエージェントの権限、hooksの入出力・停止条件は確認が必要である。

例えば、Codexではプラグインを有効化しても、同梱hookは信頼確認が済むまで実行されない。Antigravityにもhooksがあるが、設定・入出力の契約は別である。[Codexのプラグインhooks](https://developers.openai.com/plugins/build/plugins)、[Antigravity Hooks](https://antigravity.google/docs/hooks)

対応状況は製品名だけでなく、製品、App／CLIなどの実行面、バージョン、実機確認結果で管理したい。使えない機能には、別セッションでのレビューや明示実行などの代替を用意する。

MCPは、ホスト内のクライアントとサーバーをつなぎ、tools・resources・promptsなどを提供するためのプロトコルである。ワークフロー全体を管理する仕組みとは別なので、共有サービスへの接続などが必要になった段階で採用を検討できる。[MCP Architecture](https://modelcontextprotocol.io/docs/learn/architecture)

現行方針どおり、まずCodexで一連の体験を成立させ、その後に実際の差分を見て共通化する進め方を支持する。

## 5. AIレビューの入力・証拠・判断の返し方

「セキュリティ担当」「型設計担当」を作るだけでは、レビュー品質を評価できない。各レビューには最低限、次を与えたい。

- 元の要求・受け入れ条件と、対象の差分。
- 周辺コード、依存先、実際の検証結果。
- 担当する観点と、今回は確認しない範囲。
- 指摘の根拠、成立する条件、影響、確認方法。

実装者の要約だけを読ませると、実装者の誤解をそのまま引き継ぐ可能性がある。役割を分けても、独立した保証が得られるわけではない。

毎回すべての役を呼ぶ必要はない。変更内容に応じて観点を選び、指摘が競合した場合の判断役、再レビュー条件、修正回数や時間の上限まで決めると運用できる。

人間向けの出力も「要確認」だけでは足りない。例えば、次のように判断事項と確認済みの事実を分けて渡すと、レビュー負担を減らせる。

> この変更では退会後のデータを即時削除します。復元可能期間は未決定です。削除処理とテストは確認済みですが、保存方針の判断が必要です。

## 6. 中断・失敗・並行作業

自律運用では、途中状態の扱いが重要である。

- 接続断や会話終了後、どこから再開するか。
- 設定の一部だけ適用された場合、再実行するか戻すか。
- 別のエージェントや人間が同じ対象を変更した場合、どう検出するか。
- 修正とレビューが循環した場合、どこで判断を人間へ返すか。
- 共通の検証環境が壊れている場合、どの作業まで継続できるか。

既存文書には部分失敗や確認結果の陳腐化への言及がある。次は、対象、適用済みの変更、検証結果、未解決事項、次の安全な操作を引き継げる形へ具体化する段階である。

レビュー済みコミットから変更が増えた場合や、統合先が変化した場合に、何を再確認するかも決める。最初から専用の状態管理基盤を作らず、既存のPRや短い記録で成立するか試すのがよい。

## 7. 文書構成を決める基準と正本の扱い

小さいリポジトリでも、認証やデータ削除を扱うなら判断理由や検証条件が重要である。逆に、ファイル数が多くても単純な設定集なら、大量の設計書は不要かもしれない。

文書量を決める基準には、規模に加えて次を含めたい。

- 間違えた場合の影響と、戻しやすさ。
- 外部との契約や連携の数。
- 開発・運用に関わる人数。
- 判断を後から理解する必要性。

Markdownを基本に、frontmatterは状態・対象範囲など機械処理したい情報が必要なとき、Mermaidは関係や流れを図示する価値があるときに使う形が適している。

記法の統一以上に、要求、設計判断、実装、検証をたどれることが大切である。ただし、すべてに管理番号を付ける必要はない。小規模なら相互リンクで十分である。

AIによる要約には正本への参照と対象時点を付け、要約だけに決定事項を残さない。情報の競合時も、単に新しい文書を優先せず、合意された変更なのか確認できるようにする。

## 8. プラグイン自身の受け入れ条件と評価

導入先のテストが通ることと、このプラグインが役に立つことは別である。既存の受け入れシナリオに加えて、次の比較をすると効果を判断しやすい。

| 観点 | 確かめること |
| --- | --- |
| 判断の適切さ | 必要な相談を漏らさず、合意済み事項を再質問しない |
| 作業の完遂 | 準備確認だけで終わらず、依頼された作業へ進む |
| 軽微な変更への適応 | 不要な文書・設定・レビュー役を増やさない |
| 引き継ぎ | 別の会話でも決定・見送り・不足を再利用できる |
| 検証の誠実さ | 未実行や古い結果を成功扱いしない |
| 費用対効果 | 人間の確認時間、手戻り、待ち時間、実行コストがどう変わるか |

プラグインなしの場合と同じ課題で比較し、自然な依頼文でも試す。毎回同じ動作になるとは限らないため、代表的なケースは複数回試す価値がある。

人間への質問回数を減らすことだけを目標にしない。必要な相談を省けば数字は改善してしまうので、重要判断の見落としも一緒に評価する。

## 最初に試す流れ

既存の小規模リポジトリで、次の一連の流れを確かめることを提案する。

1. 通常の機能追加依頼から、既存方針と今回必要な不足を把握する。
2. 未合意の重要事項だけを相談し、実装・検証まで進める。
3. 人間が見るべき箇所と、その理由を提示する。
4. 別の会話で再開し、同じ相談や不要な整備を繰り返さない。

この体験が成立してから、複数の専門レビュー役、hooksによる強制、条件付きの自動統合へ広げると、何が実際に効いたのかを判断しやすい。
