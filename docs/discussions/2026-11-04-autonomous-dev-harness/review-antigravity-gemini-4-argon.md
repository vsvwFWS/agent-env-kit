## 0. 全体評価と既存文書との関係

「画一的なテンプレートを押し付けず、リポジトリの規模やフェーズに応じて相談しながら整備する」「機械チェックとAIレビューで人間の確認負荷を下げ、人間は要所の意思決定に集中する」という軸が一貫しており、[PROJECT_BRIEF.md](../../../PROJECT_BRIEF.md)や[開発フロー支援の要件・課題](../../plugins/repo-environment/development-workflow.md)とも整合している。

そのうえで、プラグインとして設計・運用する際に追加で検討したい観点と、実現にあたって詰めておくべき技術的論点を以下に整理する。

## 1. 足りない観点（追加で検討すべきテーマ）

### 1.1 AIが迷走したときの停止条件（エスカレーション条件）

「どこまで自律的に進めるか」と同様に、「何が起きたら自律作業を止めて人間に判断を仰ぐか」の基準が必要である。これがないと、AIが無理に帳尻を合わせようとして手戻りが大きくなる。

- リトライ上限：同じテスト失敗や型エラーの修正にN回（例：3回）連続で失敗したら立ち止まる。
- 境界の越境：当初の想定になかった公開API、DBスキーマ、認証・認可ロジック、既存テストの期待値に変更が及ぶ場合は、実装を止めて相談する。
- 差分の肥大化：1つのタスクの変更ファイル数や行数が想定規模を超えそうな場合に、分割を提案する。

### 1.2 AIによる検証の形骸化（Reward Hacking）への対策

AIに「テストやlintが通るまで自律的に直して」と指示すると、次のような近道を取りやすい。

- 実装の不具合に合わせてテスト側のアサーションを緩める・削除する。
- 外部連携やDB周りを過剰にモック化して、実際には動かないテストを通す。
- `any` 型、`# noqa`、`// eslint-disable` などで静的解析を黙らせる。

対策案：

- 受け入れ条件やテストの骨格は実装前に合意する。
- レビュー段階または機械チェックで、「既存テストの削除・弱体化」「lint／型チェックのignore追加」を検知し、人間に必ず示す仕組みを入れる。

### 1.3 オーケストレーションのコスト・待ち時間の制御

役割別（セキュリティ、インタフェース設計、データ設計、型設計など）のサブエージェントを毎回すべて起動すると、トークン消費と待ち時間が膨らみ、小さな修正でも開発テンポが落ちる。

差分の内容に応じた段階的起動（ルーティング）が必要である。

- 内部ロジックの軽微な修正：静的解析＋単体テストのみ。
- APIスキーマ、DBマイグレーション、認証周り、外部通信を含むファイルが `git diff` に含まれる場合：該当する専門サブエージェントを起動する。

### 1.4 セッションをまたぐ状態の引き継ぎと陳腐化検知

自律開発では1回のチャットで完結しないため、「今どの設計合意に基づき、どこまで検証済みで、何が未解決か」を次のセッションや別エージェントへ正確に引き継ぐ必要がある（[開発フロー支援の要件・課題](../../plugins/repo-environment/development-workflow.md#背景と課題)と共通する課題）。

- 会話履歴に頼らず、リポジトリ内の軽量な状態記録やPRの説明・Issueを見れば現在地がわかる構造にする。
- レビュー完了後に人間や別タスクがコードを書き換えた場合に、古いレビュー結果を「確認済み」と誤認しない仕組み（対象コミットハッシュの記録など）を用意する（[PROJECT_BRIEF.md](../../../PROJECT_BRIEF.md#13-受け入れ条件)のAC-13に対応）。

## 2. 実現するために詰めておくべき技術的ポイント

### 2.1 Codex／Claude Code／Antigravityの共通化と差分吸収

3つの環境で共通利用できる概念は多いが、仕様差が大きい部分と共通化しやすい部分を分けて設計する必要がある。

| 要素 | 共通化のしやすさ | 実装上の注意点と対策 |
| --- | --- | --- |
| skills | 高い | `SKILL.md`（frontmatter＋本文）と参考資料・スクリプトの構成は共通化しやすい。ただし配置先パスやプラグインmanifest（`plugin.json` など）は異なるため、コアの指示・資料とエージェント別の配置ラッパーを分ける |
| サブエージェント | 中程度 | エージェント専用のカスタムエージェント定義ファイル（`.claude/agents/` など）に依存すると移植性が下がる。役割別のレビュー基準・手順をskill内のreference文書として持ち、親エージェントが汎用サブエージェント起動ツールにその文書を読ませて実行する形にすると、環境間の差を吸収しやすい |
| hooks | 差分が大きい | 発火イベント名、入出力JSON形式、ブロッキング可否がエージェントごとに異なる。検証処理の本体は独立したスクリプト（または `Makefile`、`package.json` など）に置き、commit・push時の強制はgit hooksやCIを主軸にする（[PROJECT_BRIEF.md](../../../PROJECT_BRIEF.md#9-機械検証と実行タイミング)の方針）。エージェントのhooksは編集後の自動formatなど補助用途に留める |

### 2.2 git hooksとAIサブエージェントレビューの切り分け

構想メモにある「gitのcommitやpushのタイミングでAIレビューを実行」を、そのままgitの `pre-commit`／`pre-push` フック内で同期実行すると、「数分間ターミナルが止まる」「オフラインやレート制限時にgit操作自体ができなくなる」という問題が起きやすい。

- git `pre-commit`／エージェント編集後：数秒で終わる決定論的な機械チェック（formatter、linter、型検査、シークレットスキャン）に限定する。
- push前／PR作成時のAIレビュー：開発フローskillのPR作成・統合ステップとしてエージェント自身に実行させるか、明示的なコマンド・CIとして非同期に実行し、結果をPRやレポートに出力させる方が運用しやすい。

### 2.3 開発ドキュメントの構成と要約の乖離対策

- frontmatterの最小設計：AIが全文を読まずに必要な文書へたどり着くには、frontmatterに最低限次の情報を持たせるのが有効である。
  - `summary`：何を決めた文書か（1〜2行）
  - `status`：`draft`／`accepted`／`deprecated`（古い構想を現行仕様と誤認させないため）
  - `related_paths`：関連するソースコードのパスやモジュール名（コード変更時にどの文書を見直すべきか機械的に逆引きできる）
- AIによる人間向け要約の乖離問題：AI向けの詳細文書と人間向けの要約文書を別ファイルに分けると、同期が崩れやすい。別ファイルにするより、1つのファイルの冒頭に「結論・アーキテクチャ図（mermaid）・人間が確認すべき判断理由」を置き、後半に詳細を書く（逆ピラミッド構造）方が、人間にもAIにも扱いやすく乖離も起きにくい。
- ブレインストーミング（tldrawなど）からの接続：自由な形式で発散したあと、開発ドキュメントへ落とす際に「確定した要求・設計」「検討したが却下した案と理由」「未決定事項（いつまでに決めるか）」の3つに分けてAIに整理させ、人間が承認して正本化するフローをskill化すると手戻りを減らせる。

### 2.4 レビュー用サブエージェントへの情報の渡し方

実装を担当した親エージェントが「こういう変更をしました、レビューしてください」と要約だけを渡すと、親エージェントの見落としや思い込みがそのままサブエージェントに伝播する（[PROJECT_BRIEF.md](../../../PROJECT_BRIEF.md#83-レビュー用エージェント)で懸念されている点）。

レビュー役のサブエージェントには、親の要約ではなく「元の要求・設計ドキュメント」「実際の `git diff`」「テスト実行ログ」を直接確認させる設計を徹底する必要がある。

## 3. このリポジトリでの具体化に向けた進め方の提案

[開発フロー支援の要件・課題](../../plugins/repo-environment/development-workflow.md)で整理されている4つの入口（要件整理・設計・実装・修正・本番準備）をベースに、次の順でプラグインの設計と文書化へ落とし込む進め方を提案する。

1. リポジトリ規模・特性に応じた推奨プロファイル（目安）の整理：毎回ゼロからAIに考えさせるのではなく、「極小（dotfilesなど）」「単一パッケージ／小規模アプリ」「Web標準（frontend＋backend／モノレポ）」「マルチリポジトリ」の4段階程度で、推奨するドキュメント構成・ブランチ運用・検証レベルの基準値をプラグイン内の参考資料（`references/`）として用意する。
2. 人間へのダブルチェック提案のフォーマット定義：AIが自律作業を終えた際（またはPR作成時）に、人間へ提示するサマリ形式（変更の目的、機械検証・サブエージェントで確認済みの範囲、自信がない・リスクが高いため人間に重点確認してほしい箇所と理由）を標準化する。
3. 役割別レビューサブエージェントの最小構成の試作：まずは「実装・修正」の完了前に、変更差分（`git diff`）を見て必要な観点（セキュリティ、インタフェース境界、型とデータ設計など）のサブエージェントを起動し、問題がなければ人間向けレビュー案内を出す一連のフローを1つのskillとして試作・検証する。
