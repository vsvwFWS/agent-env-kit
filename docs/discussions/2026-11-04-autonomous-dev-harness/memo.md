## 目的

Codex、Claude Code、AntigravityなどのAIコーディングエージェントで開発するときに、AIをできるだけ自律的に動かしつつ、要所では人間が判断・レビューできる仕組みを作りたい。このプラグインは、その仕組みをリポジトリごとに構築する手助けをする。

最終的な狙いは、AIエージェントがプロジェクトの規模や特性に応じて、最適な開発フローやドキュメント構成を提案してくれることである。

## 3つのエージェントで共通に使える仕組み

| 仕組み | 現時点の理解 |
| --- | --- |
| skills | 置き場所が違うだけで、エージェントの種類に依存しない部分が多い。スラッシュコマンドやエージェントへの依頼による手動起動と、descriptionに基づくエージェントの判断による自動起動の両方に対応できる。自動起動の条件はdescriptionで柔軟に設定でき、基本的にはプロンプトで指示できる内容はすべて扱える |
| hooks | 今回の対象エージェントはすべて利用できる。特定のタイミングでスクリプトを実行し、その結果をエージェントが解釈して次の行動を決める |
| サブエージェント | 親エージェントの指示に従って動く独立したエージェント。多くのエージェントで利用できる。呼び出し方は、skillsにサブエージェントへの作業の任せ方を書く方法と、カスタムサブエージェントを事前に用意する方法がある。自律的に開発を進める仕組みなら、skillsから呼び出すのが自然と考えている |
| MCP | サーバーとツール定義のセットという理解（要確認）。サードパーティ製や自作のツールをつなぎ、エージェントが使えるツールの種類を広げる |

## プラグインの基本原則

このプラグイン自体は、対象リポジトリの開発環境を直接設定しない。開発リポジトリの状況に応じて、次の設定を促す。

- 自律的に開発を進めるための、AIエージェントの拡張機能
- 開発ドキュメントの構成
- 開発環境と依存関係の管理
- 検証の方法と手順

## 必要な要素

### ブレインストーミングと課題の整理

- 整理したアイデアを、どのようにドキュメントへまとめるかを決める。
- アイデアや課題を実現するための基本的な設計方針（アーキテクチャ、技術スタック、ツール）を検討する。
- ブレインストーミングや課題整理のチャットで得た情報を、開発ドキュメントとして整理する。
  - 相談内容からリポジトリの規模を推定し、ドキュメントの構成と整理方法を決める。
  - dotfilesのような小規模なリポジトリにはシンプルな構成を、AIエージェントでの開発を快適にするオーケストレーションツールのような比較的大規模なリポジトリには、整理された構成を提案する。

### 自律的な開発フロー

開発フローはプロジェクトによって異なるため、決まった設定ではなく、柔軟に対応できる仕組みにしたい。例として次のようなフローがある。

- 作業時はブランチを作り、プルリクエストを通じて変更を統合する。
- push時にAIエージェントによる自動チェックとレビューを実行し、問題がなければ統合する。
  - セキュリティ、インタフェース設計、データ設計、型設計などの観点でレビューし、機械的なチェックも実行する。
  - 観点ごとに担当するカスタムエージェントを用意し、それぞれが自律的にレビュー・チェックする。

### 検証方法の具体化

- lintとformatterを導入し、適切なタイミングで適用されるよう、AIエージェントの拡張を設定するように促す。
- 使用するテストフレームワークを決める。
- 受け入れ条件はプロジェクトごとに異なるため、プラグインでは定めない。未決定の場合はAIエージェントが促し、適切な条件を設定させる。観点の例はセキュリティ、パフォーマンス、可用性、ユーザビリティである。
- AIにチェックさせる方法として、次を想定する。
  - git hooksで、commit前やpush前に自動でチェックする。
  - AIエージェントのhooksを使う。
  - 役割ごとのエージェントを事前に設定し、commitやpushのタイミングで自律的にレビュー・チェックさせる。

## 開発ドキュメント

AIエージェントが読み書きしやすく、人間にも理解しやすい形が最善である。AIが適切に読み書きできる構成になっていれば、人間向けの読みやすい資料はAIに整理させることも考えられる。ただし、AIに要約させる場合は、要約が実際の開発ドキュメントと合っているかの確認が課題になる。

専用のドキュメント処理ツールも検討しているが、現段階ではない。当面はMarkdown、frontmatter、mermaidを使い、プロジェクトごとに最適な方法をAIに考えさせる。

| プロジェクトの例 | 構成の考え方 |
| --- | --- |
| dotfilesのような設定ファイル集 | シンプルなREADMEを用意し、管理対象が増えたら `doc` フォルダを追加する程度で十分 |
| frontendとbackendからなる標準的なWebアプリ（モノレポ） | サービスごとにディレクトリを分け、共通のドキュメントはルートの `doc` フォルダにまとめる |
| 同上（マルチリポジトリ） | 各リポジトリに独立した `doc` フォルダを設ける |

どちらのWebアプリ構成でも、細かい設計を並べただけのドキュメント集では必要な情報にたどり着きにくい。整理された目次や索引を用意することが望ましい。

## 人間が関与・確認する部分

| 対象 | 考え方 |
| --- | --- |
| 何を作るかの判断 | 課題整理やブレインストーミングはAIとチャットで相談する。AIに伝わりやすい記法はまだ確立できていないため、Markdownやtldrawで考えを整理してからAIに渡し、厳しく批判してもらう。実現したいことを伝え、実現方法のアイデアをAIに出させる |
| アーキテクチャ | 構成が適切かを確認する |
| 重要な設計方針・技術選定 | インタフェース境界やデータ設計を含め、妥当性を確認する |
| コードの品質 | すべてを人間がチェックするのは現実的ではない。データ型やインタフェースが適切な粒度で抽象化されているか、重要なロジックやアルゴリズムが正しく実装されているかを重点的に見る。重要な部分はAIにもチェックさせ、ダブルチェックが必要な箇所を提案してほしい |
| セキュリティ・パフォーマンス | セキュリティを担保する仕組みづくりはAIに任せ、それでも判断が難しい部分をAIが報告するのが理想。push前にセキュリティレビュー用のエージェントを実行し、機械的に確認できることは再現性のあるチェックスクリプトにする |
| AIがコンテキストを判断する仕組み | 開発ドキュメントの構成を工夫する。skillsで、ドキュメントの構成・整理の方法と、効率よく情報を探す方法を設定する。小さなプロジェクトなら全文を読ませても負担は小さい |
| アプリケーションの最終的な挙動 | Playwrightなど、作るアプリケーションに適したツールを使い、人間が確認する項目を減らす |

## 実現したい仕組み

- AIエージェントが理解しやすく、人間が書きやすい、アイデアや設計を伝える記法
- 開発ドキュメントを、AIと人間の双方が効率よく利用できるように整理する方法
- AIエージェントが自律的にレビューやチェックを実行し、人間が関与すべき部分を適切に提案する仕組み
- AIエージェントを開発の前提に置いた開発ツール
- AIエージェントが、プロジェクトの規模や特性に応じて最適な開発フローやドキュメント構成を提案する仕組み（このリポジトリで作ろうとしているプラグインの目的）
