## 0. 前提の整理

### 既存文書との重なり

メモの半分以上は、既存文書に要求として書かれている。

| メモの項目 | 既存の記載 |
| --- | --- |
| ブレスト・課題整理 | 開発フローの入口「要件整理」、依頼書 §4「新規・相談メモあり」 |
| 規模に応じた文書構成 | 依頼書 §5.1、§7「文書」 |

依頼書は[PROJECT_BRIEF.md](../../../PROJECT_BRIEF.md)、開発フローの入口は[開発フロー支援の要件・課題](../../plugins/repo-environment/development-workflow.md)を指す。

新しく加わった論点は次の5つである。

- ブレストで案を批判する役
- 観点別レビューの具体化
- push時の自動レビューから統合までの流れ
- 3エージェントへの対応
- 要約と正本のずれ

### 既存文書と食い違う点

- 「直接設定しない、促す」：依頼書では「合意した範囲を適用する」（§6.5）としている。促すだけか、合意後に適用するかを決める必要がある。
- Codex／Claude Code／Antigravityの共通対応：依頼書は「初期対応はCodex」（§3.1）、「全エージェント対応の抽象化基盤を初期から作り込まない」（§11）としている。

最初に決めることは、Repo Environmentを拡張するか、別プラグインにするかである。たとえばレビュー・チェックの仕組みは、単体でも役立つため分ける候補になる。

## 1. ハーネスの整理への補足・訂正

| 項目 | 補足 |
| --- | --- |
| 常設指示（AGENTS.md／CLAUDE.mdなど） | 一覧から抜けている。3エージェントすべてにある、最も基本的な仕組みである |
| 権限・承認モード | 抜けている。どこまで自律させるかは、実質ここで決まる |
| skills | descriptionによる自動起動はモデルの判断で、確率的に動く。「プロンプトで指示できることは全部できる」は、裏返すと「プロンプトと同じく実行が保証されない」ことを意味する。必ず効かせたいものはhooks・git hooks・CIに置く |
| hooks | 3エージェントとも使えるが、イベント名、入力JSON、ブロックやフィードバックの扱いが異なる。hooks本体は薄くし、中身はリポジトリ側のスクリプトに置くのが安全である |
| サブエージェント | 定義の形式に加え、ツール制限、モデル指定、並列実行、入れ子起動の可否が製品ごとに違う。各製品の現行仕様を確認する必要がある |
| MCP | サーバーとツール定義のセットというより、接続のためのプロトコルである。サーバーはtools、resources、promptsを公開する。ツール定義がコンテキストを消費する点と、プロンプトインジェクションのリスクがある。このプラグインのMVPには不要で、CLIやスクリプトの方が持ち運びやすい |
| 非対話実行（headless） | 抜けている。push時やCIでAIレビューを動かすには、`codex exec` のような非対話モードと認証が前提になる |
| 配布形式 | プラグインのmanifest、配置先、有効化の範囲がそれぞれ違う |

推奨する構成は次の3層である。

1. エージェントに依存しない中身：観点、文書の規則、チェックスクリプト
2. エージェントごとの薄い接続部分：skillの配置、サブエージェントの定義、hooksの設定
3. エージェントに依存しない強制部分：git hooks、CI、ブランチ保護

## 2. 足りない観点（優先度順）

### A. 人間に判断を返す条件を、宣言的に決める仕組み（最重要）

「要所で人間が判断する」の「要所」を、AIのその場の判断だけに任せると見落とす。導入先ごとに、次のようなレビュー方針を明文化させる仕組みが必要である。

- パスや変更の種類で決まるもの：認証、マイグレーション、公開API、依存の追加、インフラ、CI設定、hooks自体など。差分から機械的に検出できる（CODEOWNERSに近い考え方）。
- 内容で決まるもの：AIレビューが「要ダブルチェック」と判定したもの。
- 進めてよい量の上限：未確認の判断の上に、どこまで実装を積み増してよいか。

前者は機械で判定し、後者はAIが補う構成にすると、提案の再現性が上がる。

### B. 自律度とマージの権限

「問題がなければ統合する」は大きな判断である。次のような段階を導入先ごとに選ばせ、ブランチ保護と対応づけると整理しやすい。

- 提案だけ
- 実装してPRを作るところまで
- 低リスクに分類された変更だけ自動マージ

既定は「AIはPR作成まで、マージは人間」が無難である。

### C. AIレビューの設計

| 論点 | 検討内容 |
| --- | --- |
| タイミング | git hooksのpre-pushでAIレビューを動かすと、遅い・結果が毎回変わる・認証が要る・人間のpushまで止める、という問題がある。git hooksには決定的なチェックだけを置き、AIレビューはエージェントの作業完了時（skillやhooks）かPR時のCIに置くのが現実的である |
| 選び方 | 毎回すべての観点を起動するとコストと時間がかかる。差分のパスや種類から、必要な観点のレビュー役だけを起動する |
| 観点の持ち方 | セキュリティ、IF、データ、型ごとにskillやエージェントを量産すると、descriptionが衝突して誤起動が増える。1つのレビュー入口と観点別の参照資料の方が保守しやすい |
| 出力形式 | 重大度、確信度、根拠、`要人間確認` フラグを決めておくと、人間向けのレビュー案内（依頼書 §8.2）に集約できる |
| 修正ループ | 指摘を修正したら再レビューする。打ち切り条件と、コード変更後の結果の失効（AC-13）を決める |
| 信頼性 | 同じモデルは同じ盲点を持つ。既知の欠陥を仕込んだfixtureで検出率を測ると、レビュー役の質を評価できる |
| 入力 | 差分だけでなく、要件・設計の正本を読ませる（依頼書 §8.3）。読ませなければ、仕様との不一致を検出できない |

### D. 設計の具体化の中身（メモでは空欄）

レビューの基準になる成果物を決める必要がある。推奨は次の流れである。

- IF、データ、型をコードやスキーマで正本にする：OpenAPI、JSON Schema、DBスキーマ、型定義など。
- 文書は判断理由と境界の説明に絞る。
- この成果物を、人間がレビューする主な対象にする。

コード全体を人間が読むのは現実的ではないため、境界の定義を人間が確認し、中身は機械とAIが確認する分担がメモの方針と合う。

### E. 正本と要約のずれへの対策

- 要約・索引には参照元のリンクと、確認した時点（コミットなど）を必ず書く。
- frontmatterに最小限の共通項目を置く。例：`status`（draft／accepted／superseded）、`updated`、`related`。項目がないと機械チェックできない。
- 索引はfrontmatterからスクリプトで生成し、手書きで二重管理しない。
- リンク切れと陳腐化の検出を、maintenanceの機械チェックにする。

構成はプロジェクトごとに決める方針でも、最小限の共通の語彙は決めておくと、将来作る文書ツールに移行しやすい。

### F. 規模の推定基準と、構成を広げるきっかけ

規模を推定する判断材料を、資料として持たせる必要がある。

- デプロイ単位の数、開発者の数、想定する寿命
- 外部ユーザーの有無、扱うデータの機密性

あわせて「READMEだけからdocs/へ広げる」「docs/をサービス別に分ける」タイミングの目安が要る。縮小や統合も扱う（既存の「構成の段階的な追加」の延長）。

### G. ブレストの入力と批判役

- tldraw：`.tldr` のJSONはAIが読みにくい形式である。画像・SVGへの書き出しやmermaid化など、渡し方を決める必要がある。
- 整理と批判は別の役割にする：論点を整理する役と、反論やリスクを出す役を分けると、批判の質が上がる。
- 整理結果の型：目的、非目的、制約、決定、未決定、仮説、検証方法。入力は自由形式のまま、出力だけを揃える（依頼書の「テンプレート転記を必須にしない」と両立する）。

### H. 受け入れ条件の観点

メモに挙がっている4つ（セキュリティ、パフォーマンス、可用性、ユーザビリティ）以外に、次も候補である。

- 可観測性
- プライバシー・法令
- コスト
- アクセシビリティ
- 互換性・移行
- データの保持・削除

また、受け入れ条件はテストや確認手順に対応づけられる形で書かせる必要がある。

### I. ハーネス自体のセキュリティ

- hooksやskillsはスクリプトを実行するため、その信頼の扱いを決める。
- 文書、Issue、MCP経由のプロンプトインジェクション。
- サードパーティ製skillやMCPのサプライチェーン。
- 自動承認の範囲。

hooksやCI設定の変更そのものを、Aの「人間確認が必要な変更」に入れることを推奨する。

### J. 並行作業と長時間作業

ブランチとPRのフローに加えて、次も検討対象である。

- worktreeでの並列作業
- ブランチの命名規則
- 競合したときの扱い
- 長い作業の途中経過の記録（コンテキストをリセットしても再開できるように）

### K. プラグイン自身の評価

- descriptionによる自動起動は3エージェントで挙動が違う。検証コストは対応エージェントの数に比例して増える。
- fixture用のリポジトリとシナリオを、非対話モードで再実行できる評価の仕組みが早めに必要である。
- 効果の指標（人間のレビュー時間、手戻り、AIが人間に確認を求めた回数の適切さ）は、依頼書の段階4と合わせて決める。

## 3. 先に決めたいこと

1. 範囲：Repo Environmentに追加するか、たとえばレビュー・ゲート用に別プラグインを作るか。
2. プラグインの役割：促すだけか、合意後に適用するか。
3. 対応エージェント：3エージェント対応を今から前提にするか、Codexで一周させてから接続部分を足すか。
4. 自律度の既定値と、人間確認の条件をどう宣言させるか（A、B）。
5. AIレビューの実行場所：エージェント内、CI、git hooksのどれに置くか（C）。

まず1と2を決め、決まった内容だけを要求・未決定として該当する要求文書へ追記する進め方を推奨する。
