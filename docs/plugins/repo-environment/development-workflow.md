# 開発フロー支援の要件・課題

整理日: 2026-10-31

対象: Repo Environmentの開発フロー支援、整備状況の記録、機械チェック、構成を段階的に追加するリポジトリ全般への対応。

状態: 追加要求と設計案を整理した段階。以下の拡張は未実装・実動未検証。

この文書は[開発依頼書](../../../PROJECT_BRIEF.md)を補足し、今回追加する要求・課題・設計案の正本とする。既存要求と併せて参照する。他のプラグイン共通の仕様や、導入先へ配布する実行時資料ではない。

## 背景と課題

開発は、要件整理、実現方法の検討、設計、環境準備、実装・テスト、本番準備を往復しながら進む。段階が進むと、それまで不要だった方針、AI向け拡張、機械的な検証が必要になる。

- setup／maintenanceの結果を会話だけに残すと、次の作業や別の会話で、何が整い何が不足しているかを引き継げない。
- 未決定、未調査、未整備、意図的な見送りを区別できないと、必要な相談を漏らしたり、同じ提案を繰り返したりする。
- 設定の存在だけでは、その対象・環境で利用できるか分からない。機械で確認できることまで毎回推測するのは避けたい。
- リポジトリを一度「整備済み」とすると、後から追加する構成に必要な方針・AI拡張・検証環境の不足を見落とす。単一アプリへのDBやバッチ処理の追加、モノレポへのbackend追加などが該当する。

既存資産の再利用、規模に応じた構成、正本の重複防止は、開発依頼書の[基本原則](../../../PROJECT_BRIEF.md#5-基本原則)に従う。

## 現在の試作との関係

| 領域 | 現在の試作 | 今回求める拡張 |
| --- | --- | --- |
| 作業の入口 | setup／maintenanceの2つのskillsと参考資料 | 通常の開発依頼から、開発フローに対応するskillを選び、必要な準備を確認する |
| 状態の記録 | 既存文書を優先する記録手順 | フローや対象ごとの整備状況を継続して参照・更新する |
| 機械チェック | 導入先に存在するコマンドを調べて使う指示 | 対象と確認内容に対応づけたコマンド・スクリプトを利用する |
| 構成の段階的な追加 | 構成追加に応じた状態管理・確認手順は未実装 | 追加する構成と既存部分への影響に応じて不足を確認する。モノレポでは共通部分、各アプリ、連携部分も区別する |

現在の記録手順は[共通の作業規則](../../../plugins/repo-environment/references/workflow.md#記録の最小構成)を参照する。既存の正本がなければ `docs/agent-environment.md` を提案し、個人の参照先は[関連リポジトリ参照](../../../plugins/repo-environment/references/related-repositories.md#登録する情報)で `.codex/repo-environment.local.md` を提案している。

今回の保存先案は、その手順を既に変更したものではない。現在の配布内容は[配布README](../../../plugins/repo-environment/README.md)、確認済みの範囲は[検証記録](../../../tests/repo-environment/validation.md)を正本とする。

## 開発フローと確認する仕組みの例

次は確認観点の例であり、固定の工程や全項目の導入を要求しない。機能追加では既存の決定・基盤を再利用し、段階を省略・往復できる。プロジェクト全体を一つの段階に固定せず、今回の作業について必要な準備を見る。

| 作業 | 確認する仕組み・方針の例 |
| --- | --- |
| 要望・課題・要件の整理 | 文書の正本と入口、リポジトリ内管理か文書専用リポジトリ参照か、規模に応じた文書構成、決定・未決定、受け入れ条件 |
| 実現方法の検討 | 制約、選択肢の比較、採用理由、試作で確かめること |
| アーキテクチャの決定 | 責務と依存の境界、開発・本番での動かし方、検証可能性 |
| 計画・データ設計 | タスクの分割と依存関係、データやAPIの契約、変更・移行方針 |
| 開発環境の準備 | 起動方法、linter・formatter、テスト方針とフレームワーク、AI拡張 |
| 実装・テスト | 抽象化・共通化の判断基準、開発環境での動作確認、テスト、レビュー、必要に応じたCI・開発環境向けCD |
| 本番環境で動かす準備 | 配備、環境設定、監視、復旧、運用手順 |

タスク管理の入口は要件整理から置き、詳細なタスクは設計に合わせて分割する案がある。テストは要件段階で受け入れ条件、設計段階で検証方法を考え、環境準備で実行手段を整える。抽象化の基準も実装前に最小限を置き、実装の知見で見直す。これらの具体的な進め方は導入先に合わせて決める。

## 追加要求

### 整備状況を記録して引き継ぐ

setup／maintenanceで、開発に必要なフローのどこが整い、どこが不足しているかを導入先ごとに記録・更新する。別の会話でも既存の判断と不足を把握できるようにする。共有するプラグイン本体の保存場所と、導入先固有の状態を分ける。

### 開発依頼から確認を始める

開発フローに対応するskillsを用意し、依頼内容とdescriptionからモデルが選択する形を主な入口とする。段階の判定をhooksに担わせない。skill本文で記録と実態を参照し、今回の作業に必要な未決定事項や不足を案内する。

具体的なskillの数・分割は未決定。descriptionによる選択が適切に働くかは通常の依頼で検証し、明示的な呼び出しだけの成功で代替しない。具体的な製品設定を採用する際は、公式仕様と実環境を確認する。

### 機械で確認できることは実行して確かめる

確認可能な項目には、既存コマンドやスクリプトを利用できるようにする。導入先の対象範囲と実行方法を対応づけ、成功・失敗・実行不能・未実行・対象外を区別する。

コマンドが動くこと、検証が通ること、その検証が今回の要件を十分に確かめることは別の判断とする。検証の実体と呼び出しの分担は、開発依頼書の[機械検証と実行タイミング](../../../PROJECT_BRIEF.md#9-機械検証と実行タイミング)に従う。

### 構成の段階的な追加に対応する

後から機能・技術・実行環境などの構成を追加するリポジトリ全般を対象とする。確認する範囲はアプリやディレクトリの単位に限定せず、追加する構成と既存部分への影響に応じて決める。新しいディレクトリを作らない追加も含め、既存の方針・基盤・整備状況を引き継ぎながら、追加に必要な不足を確認する。

モノレポへのbackend追加はその一例とする。この場合はリポジトリ共通、frontend、backend、両者の連携部分を区別し、frontendが整備済みでもbackendや連携部分の準備が完了していると扱わない。

## 設計案

以下は要求を実現する候補であり、保存形式や実装仕様の確定ではない。

### 導入先の保存先と正本

導入先ルートに `.repo-environment/` を置き、共有する状態をGitで管理する案を検討する。例として `project.toml` に方針・参照先・整備状況、必要時のみ作る `local.toml` に個人のローカルパスを置き、後者をGit除外する。フォルダ名、ファイル名、TOML形式はいずれも未採用。

この保存先はプラグインが読む独自の情報であり、エージェント本体が自動認識する設定を想定しない。要件・設計・開発手順の本文は既存の正本へ置き、保存先には参照と状態を記録する。文書専用リポジトリを使う場合も、既存の参照設定を利用する。

### 記録する情報

| 情報 | 記録する内容の案 |
| --- | --- |
| 対象範囲 | 追加する構成と影響する既存部分。必要に応じて共通部分、各アプリ、連携部分と対象の場所 |
| 項目と必要性 | 文書、方針、AI拡張、機械チェックなど。どの作業で必要になるか |
| 判断 | 未決定、採用、見送り、不要などと、その根拠・参照先 |
| 整備・確認状況 | 未確認、未整備、設定済み、実行確認済みなど。判断とは別に記録する |
| 実行方法と結果 | コマンド・スクリプト、作業ディレクトリ、確認した対象・時点・結果 |
| 保留と再確認 | 保留理由、再検討する条件、関連設定の変更など確認を更新するきっかけ |

状態の名称と項目構造は未決定。記録がない場合は実態を調べ、未決定・未整備と即断しない。個別機能の進捗は既存の計画・タスクを参照し、開発基盤の整備状況との二重管理を避ける。

### 開始時の確認と声がけ

各フローのskillから共通の確認手順を参照する案とする。今回の作業と対象を把握し、関係する記録を読み、必要な範囲の実態を確認する。不足があれば影響と最小の対応をまとめ、合意した整備・検証後に記録を更新する。相談と適用の境界は開発依頼書の[必要な判断をまとめて相談する](../../../PROJECT_BRIEF.md#63-必要な判断をまとめて相談する)に従う。

声がけは、今回の作業に必要な項目が未決定・未整備の場合に絞る。見送り済みの項目は再検討条件に達するまで繰り返し促さない。機械チェックは、開始時の軽い確認、変更後の関連テストなどに分け、毎回すべてを実行する構成を避ける。

### 構成追加時の確認範囲

構成の追加依頼を起点に、実装やディレクトリ作成の前から必要な準備を確認する案とする。単一アプリへのDB追加なら、既存の整備状況を引き継ぎ、データの扱いに関する方針やDBとの連携を検証する方法の不足を確認・記録する。ディレクトリの追加の有無で確認の要否を決めない。

モノレポへのbackend追加では、共通方針・基盤を参照し、backend固有の不足を記録する。後にfrontendとの連携を始めたら、API契約や結合テストを別途確認する。

既存の共通設定を各対象へ複製することは前提にしない。共通設定の変更時に、どの対象の確認結果を見直すかは設計時に具体化する。

## 未決定事項

- 保存先、ファイル形式、状態の名称と項目構造、ファイルを分割する基準。
- 開発フローごとのskillの数・責務・descriptionと、既存の専門skillsとの役割分担。
- コマンド・スクリプトの配置、登録方法、実行条件、結果の受け渡し、必要な実行時依存。
- 追加する構成と影響する既存部分の識別方法、共通設定の参照と個別設定の扱い、連携対象の表現。モノレポのアプリ単位やディレクトリに限定しない対象の表し方。
- 保留事項の再通知条件、記録の陳腐化を判断する根拠、確認結果を更新する範囲。
- 現在の記録手順からの移行方法。既存文書・ローカル設定・手動変更をどう引き継ぐか。

## 受け入れシナリオ案

以下は追加要求・設計案を具体化するための候補であり、検証済みの結果ではない。既存の[受け入れ条件](../../../PROJECT_BRIEF.md#13-受け入れ条件)と併せて扱い、実動検証は配布元以外のリポジトリで行う。

| シナリオ | 確認する振る舞い |
| --- | --- |
| 通常の依頼から選択 | skill名を指定せず「実現方法を検討したい」「機能を追加して」と依頼し、適切な入口が選ばれる。軽微な文言修正では不要な全体確認を始めない |
| 別の会話で再開 | setupで記録後、別の会話で今回の作業に関係する判断・不足・正本を引き継げる |
| 必要な不足を案内 | 今回必要なテスト方針が未決定なら声をかけ、関係しない未決定事項まで一括で決定させない |
| 見送りと再検討 | 見送り理由と条件を記録し、同じ状況で繰り返し促さず、条件が変わったときに再確認する |
| 機械チェック | 正しい対象・作業ディレクトリで実行し、成功・失敗・実行不能・未実行を区別する。実行成功だけで方針の十分性まで保証しない |
| 記録と実態のずれ | 記録がなくても既存設定を調べる。記録後に関連設定が変更されたら、以前の結果を現在の確認済み証拠にしない |
| 単一アプリへDBを追加 | 新しいディレクトリを作らずにDBを追加する。既存の整備状況を引き継ぎ、追加に必要な方針・検証の不足と既存部分への影響を確認する |
| backendを後から追加 | frontend整備後、まだ存在しないbackendの追加を依頼する。共通部分を再利用し、backend固有の不足を確認・記録する |
| frontendとbackendの連携 | 各アプリ単体の整備・検証と、API契約・結合テストなどの連携確認を区別する |

実施手順と結果は、具体化した時点で[検証資料](../../../tests/repo-environment/README.md)へ追加する。この文書の作成は実動検証の実施を意味しない。
