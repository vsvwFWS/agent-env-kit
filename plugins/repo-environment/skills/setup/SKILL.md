# リポジトリのセットアップ

対象の開発リポジトリに、その段階で必要な最小限のAI開発環境を整える。プラグインのインストールと、導入先への設定適用を区別する。

最初に[共通の作業規則](../../references/workflow.md)を読む。対象はユーザーが指定したリポジトリ、指定がなければ現在の作業先とする。プラグインの保存場所を対象リポジトリと取り違えない。

## 進め方

1. 相談メモ、要求、既存の指示・コード・依存・検証・文書と未コミット変更を調べる。空のリポジトリでも、目的と次に必要な判断から進める。専用テンプレートへの転記を要求しない。
2. 明示的な合意、実装上の慣例、候補、未決定、不整合を区別する。既存の仕組みを再利用し、不足とその影響を示す。調査済みのことは再質問しない。
3. 必要な作業を選ぶ。各項目の採用は任意とし、「現状で十分」も認める。
   - 常設指示と開発文書：重要な判断規則、正本の所在、実行可能な検証の入口を整える。
   - 機械検証：既存のlint・型検査・テスト・buildを優先する。新設は対象の技術と合意に合わせる。
   - 拡張：不足を補う候補の探索・提案・導入には[拡張の選定](../../references/extensions.md)を読む。
   - 関連リポジトリ：別の仕様・契約・コードが必要なら[参照設定](../../references/related-repositories.md)を読む。
4. 未合意の主要技術、依存、外部接続、既存方針の変更について、推奨案・理由・代替案・影響をまとめて相談する。既に合意済みの通常作業は進める。
5. 作成・変更・削除する対象、再利用するもの、検証方法を具体化し、合意した範囲を小さく適用する。アプリ本体の雛形作成や機能実装は、依頼された範囲に含まれる場合だけ行う。
6. 設定の読み込み、実際の検証コマンド、必要な接続を確認する。結果と次回の再開に必要な記録を、共通規則に従って残す。

セットアップ済みの対象で呼ばれたら、現在の状態を確認して不足だけを扱う。導入し直したり、同じ指示や設定を追加したりしない。全体の見直しが必要ならメンテナンスの手順へ案内する。
