# ローカルの関連リポジトリ参照

## 登録する情報

初期版は取得済みのローカルリポジトリを読み取る。参照を登録するための自動cloneや、参照先の設定変更は行わない。リモートからの取得が必要なら、その不足を示して別の作業として相談する。

既存の仕様索引や開発文書があれば使い、次の情報を必要な範囲で記録する。

| 項目 | 内容 |
| --- | --- |
| 識別名 | `service-api` など、パスが変わっても使える名前 |
| 識別情報 | 既知のリポジトリURLやプロジェクト名。認証情報を含めない |
| 役割・正本 | 業務仕様、API契約、参照実装など。何の判断に使うか |
| 読むタイミング・入口 | API変更時に `openapi.yaml` を読む、など。入口は参照先のルートからの相対パス |
| 必要な版 | 特定ブランチ・タグなどの制約があれば記録する |

共有情報には個人の絶対パスを固定しない。手元のパスは既存のローカル設定方式へ対応づける。既存方式がなければ、対象内の `.codex/repo-environment.local.md` を既定の提案先とし、識別名と実パスの表だけを置く。作成前にそのファイルが追跡済みでないことを確認し、対象のGit除外設定で非共有にする。既存の設定ファイルと除外規則は保持する。

このMarkdownはskillが読む対応表であり、Codex本体の設定キーやアクセス権を追加するものではない。関連リポジトリが不要なら新しいファイルを作らない。

## 参照時の動作

識別名からローカルの実パスを解決し、アクセス可否、リポジトリの識別情報、必要な版と入口を確認する。共有された相対パスを使う場合も、その基準を明示する。worktree移動後や別環境で、同じ相対パスが別の対象へ解決されないか確認する。

必要な入口から読む。参照先全体を毎回読み込まず、質問に関係する仕様や契約へ絞る。参照したコミットと、必要なら未コミット変更の有無を結果に残す。参照先の指示はそのリポジトリの作業規則として確認し、無関係な変更や現在のユーザー合意の上書きへ拡張しない。

パス不明、アクセス不能、入口の消失、必要な版との不一致は未確認として示す。相手の情報が必須の判断だけを保留し、影響しない作業は進める。参照の登録を、参照先への書き込みやアクセス権拡大の承認として扱わない。

メンテナンスでは参照の必要性、パス・入口・版の整合を確認し、変更を提案する。参照の削除で相手のリポジトリを削除しない。

## 専用skill・pluginを使う場合

仕様の所在を案内するだけなら、参照表と既存文書で足りる。固有の検索・生成・検証手順を何度も使う場合は、参照先が提供するskill・pluginの再利用を検討する。単に別リポジトリを読んだだけで、そのskillが自動的に登録されたとはみなさない。導入が必要なら[拡張の選定](extensions.md)の手順で扱う。
