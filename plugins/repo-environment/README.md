# Repo Environment

Codexで、開発リポジトリに合わせたAI開発環境を整備・見直すプラグインです。配布用識別子は `repo-environment`、初期版は `0.1.0` です。

**試作版です。** skillsと参考資料、リポジトリ単位の導入手順を用意しています。デスクトップアプリでの導入・動作・適用範囲は未検証です。初期の検証対象はCodexデスクトップアプリ、関連リポジトリの参照対象はローカルに取得済みのものです。

## できること

- [setup](skills/setup/SKILL.md)：相談メモや既存構成から、指示・開発文書・検証手順の不足を調べ、合意した最小構成を適用する。
- [maintenance](skills/maintenance/SKILL.md)：合意・手動変更・現在の実態を比較し、必要な修正・統合・削減を行う。
- 必要に応じ、公式／サードパーティの拡張を探索・提案し、採用合意後に利用可能な導入手段で設定する。
- 関連リポジトリの役割・参照タイミング・入口と、手元の配置の対応を整える。

skillsはCodexへの作業指示です。検索、設定編集、導入などはそのセッションで利用可能なツールを使います。本パッケージにMCPサーバー、hooks、専用インストーラー、実行時ライブラリ依存はありません。追加機能が使えない場合は、未実行の段階と必要な操作を報告します。

## リポジトリ単位で試す

まずは検証用の別リポジトリへ導入します。以下は2026-10-29に確認した[公式のplugin配置・導入仕様](https://developers.openai.com/plugins/build/plugins)に基づく手順です。利用するアプリの版で設定が認識されることを確認してください。

### 1. 配布対象だけをコピーする

配布元の `plugins/repo-environment/` の内容だけを、導入先の `.agents/plugins/repo-environment/` へコピーします。パスは導入先の既存配置に合わせて変更できます。

POSIXシェルでの初回コピー例です。2つのパスを実在する場所へ置き換え、同じ実行環境のパスを使ってください。WindowsのアプリからWSL上のパスが使えるかは別途確認が必要です。

```sh
plugin_source='/absolute/path/to/agent-env-kit/plugins/repo-environment'
target_repo='/absolute/path/to/target-repository'
test -f "$plugin_source/plugin.json" &&
test -d "$target_repo" &&
test "$(git -C "$target_repo" rev-parse --show-toplevel)" = "$target_repo" &&
test ! -e "$target_repo/.agents/plugins/repo-environment" &&
mkdir -p "$target_repo/.agents/plugins" &&
cp -R "$plugin_source" "$target_repo/.agents/plugins/repo-environment"
```

コピー例は、導入先がGitルートと一致しない場合も停止します。既にコピー先がある場合は上書きせず、更新手順で差分を確認します。

### 2. 導入先のmarketplaceへ登録する

導入先の `.agents/plugins/marketplace.json` で、プラグインの場所を案内します。以下は既存カタログがない場合の例です。`my-project-env` は他の検証先と重複しない名前へ置き換えてください。同じ識別子を別内容に使うと、共有キャッシュや設定と衝突する可能性があります。

```json
{
  "name": "my-project-env",
  "plugins": [
    {
      "name": "repo-environment",
      "source": {
        "source": "local",
        "path": "./.agents/plugins/repo-environment"
      },
      "policy": {
        "installation": "AVAILABLE",
        "authentication": "ON_INSTALL"
      },
      "category": "Productivity"
    }
  ]
}
```

既存カタログがある場合は、その名前と他のエントリを保持して `plugins` に1件を追加します。同名エントリがあれば内容を比較し、重複追加しません。`source.path` の基準は導入先のリポジトリルートです。

### 3. 対象プロジェクトで有効化する

導入先の `.codex/config.toml` に、次の設定を追加または統合します。既存の同名テーブルがある場合は、そこにあるキーを確認して編集します。

```toml
[plugins."repo-environment@my-project-env"]
enabled = true
```

`@` の後ろは実際のmarketplace名へ合わせます。プロジェクト設定を読み込むには、Codexでそのプロジェクトを信頼済みとして扱う必要があります。信頼設定はユーザーが確認してください。

対象をデスクトップアプリで開いて再起動し、Plugins画面でmarketplaceとプラグインを確認します。アプリが導入操作を求める場合は表示内容を確認して進め、新しい会話でskillsが利用可能か確かめます。

公式仕様では、インストール済みのコピーにユーザー領域の共通キャッシュが使われ、プラグイン画面の操作がユーザー設定へ保存される場合があります。**カタログを対象に置くだけでは、他のリポジトリへの適用除外を保証しません。** 全体での有効化を要求される場合はこの試行を止め、プロジェクト設定だけで扱えるかを確認します。他のリポジトリで有効になっていないことも、導入検証に含めてください。

## 呼び出す

対象リポジトリの新しい会話で、プラグインのsetupまたはmaintenance skillを選択して依頼します。表示される正式なskill名は選択UIで確認してください。

セットアップの依頼例：

> Repo Environmentのsetup skillを使って、このリポジトリのAI開発環境を整えてください。相談メモはPROJECT_BRIEF.mdです。既存の決定を引き継ぎ、未合意の主要技術だけ相談してください。

メンテナンスの依頼例：

> Repo Environmentのmaintenance skillを使って、現在の構成を見直してください。人が編集した指示を保持し、採用した拡張と関連リポジトリの参照も確認してください。

初期の呼び出し確認はskillを明示して行います。暗黙の選択はCodexの標準設定に従います。プラグインの導入は、このリポジトリへの設定適用や、外部拡張の追加承認を兼ねません。

## 更新・無効化・削除・復旧

- **更新**：コピー元のバージョンと差分、コピー先の手動変更を比較し、旧版へ戻せる状態で配布フォルダを更新します。コピー失敗時は適用済みファイルを確認し、旧版の退避から対象だけを復旧します。アプリを再起動し、読み込まれた版とskillを確認してください。プラグイン更新では、setupが作った開発文書や検証設定は変更しません。
- **無効化**：対象のplugin設定を `enabled = false` にし、新しい会話でskillが有効になっていないことを確認します。共有キャッシュは残ることがあります。
- **削除**：まず対象で無効化し、他の利用先への影響を確認します。対象のカタログから該当エントリを取り除き、追加した配布フォルダだけを削除します。明示的な `enabled = false` は、ユーザー全体の設定から再度有効にならないよう、必要なら残します。共有キャッシュやユーザー全体のアンインストールは別の操作として扱います。
- **成果物**：導入先で合意した指示・文書・検証設定・参照情報は残します。削除する場合は別途その範囲を合意します。
- **復旧**：変更前の配布フォルダ、カタログの該当エントリ、設定キーを復元します。既存ファイルやユーザー差分を丸ごと巻き戻しません。再起動後も反映されない場合は未確認として扱い、キャッシュを無差別に消しません。

## 設計上の境界

常設指示と合意の記録は導入先の既存文書を優先します。関連リポジトリの共有情報と個人のローカルパスは分け、実際の読み取り権限はホスト環境に従います。参照先の自動clone、複数リポジトリへの横断変更、全体設定への自動展開は初期版の対象外です。

プラグインの対応OS・WSL・アプリのバージョン範囲は、実動検証ができた範囲で宣言します。現時点では、どの環境についてもデスクトップでの動作保証はしていません。
